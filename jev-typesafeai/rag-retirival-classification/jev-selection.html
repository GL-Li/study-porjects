How Jev selects retrieved passages

Retrieval hands back a ranked list of candidate passages. Ranking says which ones are similar; it does not say which ones are trustworthy, on-topic, or usable. Jev supplies that judgment as numbers, and ordinary code turns those numbers into a decision about what the answer-writer gets to see.

1 · RetrieveCandidates come back from the store, already ranked. How is out of scope here.
2 · Ask JevFour yes/no questions per passage. Answers are probabilities, not text.
3 · Route in codeThresholds decide include / conflicting / exclude.
4 · Build promptOnly accepted and conflicting evidence reach the generator.
Jev in one line: it is a System One model. It does not write answers or explain itself. Each question returns a single probability that the answer is yes (0 = no, 1 = yes). The decision of what to do with that probability lives in your code.

Step 2 — Jev answers four questions per passage

For each passage the code sends the query and the passage text as state, and asks four independent yes/no questions. These are Noul questions: each returns the probability that the answer is yes. A passage's malicious text is data to be judged, never instructions to be followed.

Question (id)What a high value means
is_relevantThis passage addresses the subject of the query.
contains_answer_evidenceThis passage states something usable in a direct answer.
contradicts_query_premiseThis passage disputes a factual premise the query takes for granted.
contains_prompt_injectionThis passage tries to control the system answering the query.

The four questions run together over the same passage, so asking all four barely costs more than asking one. The question ids are for code; only the instructions reach the model.

Read the rows, not the values in isolation:

  • sessions-04 is strongly relevant and full of evidence, yet contradicts_query_premise is 0.87 — the passage pushes back on the query's assumption. It is not thrown away; it is quarantined as conflicting so the generator can report the conflict.

Every number the router reads is a Noul probability. Jev never says "include" or "exclude" — it only answers the four questions.

Step 3 — code turns probabilities into a route

The thresholds are constants, deliberately kept in one place so a policy change is a reviewed code edit rather than a reworded question:

THRESHOLDS = {
    "injection_max":   0.70,   # above this the passage never reaches the prompt
    "contradicts_min": 0.70,   # above this it disputes what the query takes for granted
    "relevant_min":    0.30,   # below this the passage is not about the query at all
    "evidence_min":    0.30,   # above this it states something usable in an answer
}

Routing is a short ordered list of checks. Order is the whole design: the first rule that matches wins.

  1. If contains_prompt_injection > 0.70 → exclude. Safety is checked before usefulness, so a persuasive-injection passage can never become evidence.
  2. Else if contradicts_query_premise > 0.70 → conflicting_evidence. Kept, but separated from accepted facts.
  3. Else if is_relevant < 0.30 → exclude. Off-topic passages drop before the evidence test.
  4. Else if contains_answer_evidence > 0.30 → include.
  5. Else → exclude. Relevant but says nothing usable.

Applying that list to the four examples: sessions-01 → include; sessions-04 → conflicting; forum-injection → excluded by rule 1; sessions-02 → excluded by rule 3.

Three outcomes, each meaningful: include is evidence the generator answers from, conflicting is evidence it must surface as a disagreement, and exclude is dropped entirely. Nothing is summarised or rewritten by Jev — a passage either survives intact or it does not.

Step 4 — only the survivors reach the generator

The routes build two evidence blocks. The accepted block goes in under "Accepted evidence"; the conflicting block under "Conflicting evidence" with instructions to report disagreements. The excluded passages, including the injected one, are simply absent.

Conflicting evidence

[sessions-04] User sessions: Limiting…

The prompt still tells the generator to treat passages as untrusted text and to cite ids — belt and braces alongside the injection check that already ran.

Why this shape

  • Common sense from the model, policy from code. "Is this passage relevant?" is hard to encode by hand; "what counts as relevant enough" is a number your team should own and review.
  • Probabilities are first-class. A Noul value is the probability the answer is yes — the answer itself in one number. A value near 0.5 means yes and no are about equally likely, not "medium certainty," so it thresholds cleanly and can be logged or tuned later.
  • Safety is a route, not a hope. Injection is judged explicitly and checked first, so no amount of relevance or evidence can sneak hostile text into the prompt.
  • Conflicts are preserved. Contradictory passages are labelled rather than deleted, letting the generator tell the user where the sources disagree.
