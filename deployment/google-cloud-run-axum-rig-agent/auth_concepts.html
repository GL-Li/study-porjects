1. The authentication model

Authentication answers "who is this?" and authorization answers "are they allowed to do this?". This app does both in one place: you prove an email + password once, then every later request carries a session that says who you already are.

Two separate secrets are involved, and confusing them is the classic mistake:

SecretWho knows itStored howUsed for
The user's password Only the user Hashed with argon2id in users.json (password_hash) Proving identity at /login
SESSION_SECRET The server only An env var / Secret Manager, never persisted with users Signing & verifying session JWTs

Code: AuthState.session_secret (auth.rs:46), User.password_hash (auth.rs:132).

Key idea. The server never needs to remember who is logged in. The user carries a signed token that is the proof. That is what lets the service run on stateless instances that come and go.

2. Password hashing

Never store the password itself

If the user store leaks, plaintext (or reversibly encrypted) passwords hand the attacker every account, and users reuse passwords elsewhere. Instead we store a one-way hash: a fixed-length fingerprint from which the original cannot be recovered, but which can be recomputed to check a candidate.

A hash is not just "hash it once"

Fast hashes (MD5, SHA-256) are the wrong tool: a GPU tries billions of guesses per second. Password hashing therefore uses a deliberately slow, memory-hard algorithm. This app uses argon2id via the argon2 crate.

Salt

A salt is random data mixed into each hash so two users with the same password get different hashes. This defeats precomputed "rainbow table" attacks and hides which users share a password. The salt is not secret; it is stored next to the hash.

The PHC string

argon2 does not store the hash and salt in separate columns. It emits one self-describing text string, the PHC format:

$argon2id$v=19$m=19456,t=2,p=1$c29tZXNhbHQ$RdescudvJCsgt3ub+b+dWRWJTmaaJObG
      │         │        │           │           └── the hash (base64)
      │         │        │           └── the random salt (base64)
      │         │        └── cost parameters: memory, iterations, parallelism
      │         └── algorithm version
      └── algorithm: argon2id

Because the parameters and salt travel with the hash, verification is self-contained and the cost can be raised later without breaking old hashes.

Hash, then later verify

Hashing happens once at account creation / password change; verification happens on every login by re-hashing the candidate with the same salt and parameters and comparing.

// create: hash_password(password) -> PHC string
let salt = SaltString::generate(&mut OsRng);          // fresh random salt
Argon2::default().hash_password(password.as_bytes(), &salt)

// check: verify_password(candidate, stored_hash) -> bool
let parsed = PasswordHash::new(stored_hash)?;         // parse salt+params
Argon2::default().verify_password(candidate.as_bytes(), &parsed).is_ok()

Code: hash_password (auth.rs:344), verify_password (auth.rs:354). Both use OsRng, the operating system's cryptographically secure RNG.

Verification is intentionally slow. argon2 is designed to take ~tens of milliseconds. That is the point — it also slows attacker brute force — so never "optimize" it away.

3. Sessions & why HTTP needs them

HTTP is stateless: each request arrives with no memory of the previous one. Without help, the server could not tell the second request from a stranger. Authentication solves this by issuing a session at login: a short credential the client presents on every subsequent request.

Definition. A session is the server's ongoing recognition that a client is already authenticated as a particular user, sustained across requests that are otherwise forgotten. It rests on four things: a verified identity (sub), a proof the client can replay (a signed JWT), a validity window (exp), and a carrier plus a rule that present and accept it (an HttpOnly cookie and the auth middleware). Here it has no server-side record — the token is the session.

There are two broad designs:

Server-side sessionClient-side token (this app)
Where state livesServer keeps a session table keyed by an opaque IDToken carries the state; server keeps nothing
Cookie holdsA random IDA signed JWT
RevocationDelete the row — instantHard without extra state (see §11)
Scales toNeeds shared session store for many instancesAny number of stateless instances

This service is designed for stateless Cloud Run instances, so it picks the token approach: the session lives entirely in the JWT the client carries.

Session lifetime (TTL)

A session should not last forever. SESSION_TTL_SECS (default 28 800 = 8 hours) sets how long a token stays valid; when it expires, the user must log in again.

Code: session_ttl set in AuthState::from_env (auth.rs:61), embedded as exp in issue (auth.rs:81), default 28 800.

4. JSON Web Tokens (JWT)

A JWT is a compact, URL-safe string with three base64url parts joined by dots:

header . payload . signature
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9 . eyJzdWIiOiJhQGIuY29tIiw... . dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
  • Header — metadata, here {"alg":"HS256","typ":"JWT"}.
  • Payload — the claims, i.e. the facts we assert (see below).
  • Signature — proves the header + payload were produced by someone holding the secret and were not tampered with.

Claims

In this codebase the payload is the Claims struct serialized to JSON:

{
  "sub": "user@example.com",   // subject: who this token is about
  "exp": 1730000000,           // expiry, Unix seconds
  "must_change": false         // custom claim: forced password change pending
}

sub and exp are registered JWT claim names; must_change is a private claim specific to this app. Claims are only encoded, not encrypted — anyone can read them, so never put secrets in a payload.

Code: Claims (auth.rs:110).

Signing: HMAC-SHA256 (HS256)

The signature is HMAC-SHA256(secret, header + "." + payload). The same SESSION_SECRET both signs and verifies (symmetric). Anyone who knows the secret can forge tokens, so the secret must be strong and private — hence the 16-character minimum and Secret Manager in production.

// sign at login
encode(&Header::default(), &claims, &EncodingKey::from_secret(&self.session_secret))

// verify on every protected request
decode::<Claims>(&token, &DecodingKey::from_secret(&self.session_secret), &Validation::new(Algorithm::HS256))

Code: issue (auth.rs:78) and claims_from_headers (auth.rs:94). Validation enforces the algorithm and checks exp, rejecting expired tokens.

Signed with the secret — not stored in it. A JWT contains only the header, the payload, and the signature; SESSION_SECRET is an input to the HMAC, never part of its output. Decoding a token reveals the claims but cannot recover the key, because HMAC is one-way: the only way to obtain the secret is to guess it, which is infeasible for a long random key. A stolen token can be replayed until exp, but it cannot be used to forge tokens for other users.
Why pin the algorithm. Passing Validation::new(Algorithm::HS256) avoids the classic JWT flaw where an attacker switches the header to alg: none or to an asymmetric algorithm to bypass verification. Always reject the algorithm you do not expect.

5. The signing secret

Every JWT is signed with one long-lived key, SESSION_SECRET. It deserves its own section because it is the single point on which every token's integrity rests — and because its name invites a wrong assumption.

Not per-session, despite the name

The name describes what it protects (the session mechanism), not how long it lives. It is one value shared by every session and every instance, which is exactly what lets any instance verify a token that another instance issued — with no server-side session table.

ThingLifetimeHeld by
SESSION_SECRET (signing key)Long-lived; until rotatedServer only (env / Secret Manager)
Session token (JWT)session_ttl, then expClient, in the cookie
Claims (identity, exp, flag)Per tokenClient, inside the signed payload

Where it comes from

The Rust code never creates it; AuthState::from_env reads it from the environment and fails fast if it is missing or shorter than 16 characters.

  • Local dev: you generate it — export SESSION_SECRET="$(openssl rand -base64 32)" — and keep it in the shell or a gitignored .env (loaded by dotenvy).
  • Cloud Run: scripts/setup_secrets.sh creates it once in Secret Manager as session-secret; the deploy mounts it as the SESSION_SECRET env var at runtime.

Code: read at AuthState::from_env (auth.rs:55), copied into session_secret (auth.rs:70).

If it leaks, sessions are forged

HS256 is symmetric: the key both signs and verifies, so whoever holds it can mint a valid cookie for any user. An attacker could set sub to any email, push exp far into the future, set must_change = false to satisfy the route guards, and reach / and /chat — with no password. It does not expose passwords (those are argon2-hashed separately) or the DeepSeek/GCS secrets, though a forged session can still consume the agent indirectly.

Only rotation kills a leaked key. Because there is no server-side session state, individual tokens cannot be revoked; adding a new Secret Manager version of session-secret invalidates every token at once — forged ones included — and logs everyone out. A leaked token is bounded by exp; a leaked secret is not, so rotate immediately and treat the user store as suspect if it leaked too.
Why symmetric, and the alternative. HS256's one key is simple and fast, but a verifier can also forge. Asymmetric signing (RS256/EdDSA) keeps the private key on the signer and lets anyone verify with a public key, so a compromised verifier cannot mint tokens — at the cost of more moving parts.

6. Cookies & their security flags

A cookie is a small name=value pair the server sets with Set-Cookie; the browser then automatically sends it back in the Cookie header on every matching request. That automatic replay is exactly what makes cookies convenient for sessions — and dangerous if mishandled. This app sets:

session=<jwt>; Path=/; HttpOnly; SameSite=Lax[; Secure]
AttributeWhat it doesWhy it matters
HttpOnly JavaScript cannot read the cookie via document.cookie A cross-site-scripting (XSS) bug cannot directly steal the session token
Secure Cookie is only sent over HTTPS Stops the token being sniffed on plaintext HTTP. Controlled by COOKIE_SECURE (default on; must be off for local http://)
SameSite=Lax Cookie is not sent on most cross-site requests Mitigates cross-site request forgery (CSRF)
Path=/ Cookie applies to the whole site Session needed on all routes

Logout clears the cookie by setting it to the empty string with Max-Age=0, which tells the browser to delete it immediately.

Code: session_set_cookie (auth.rs:443), session_clear_cookie (auth.rs:451), session_cookie reads it back (auth.rs:429).

HttpOnly is not a silver bullet. It protects the cookie from being read by scripts, but an XSS bug can still make requests using the cookie. Defense-in-depth matters: escape output, validate input, and keep SameSite on.

8. Middleware & route guards

Middleware is code that runs around a handler: it can inspect the request, decide to stop, or pass control on with next.run(req). The diagram below shows how a handler sits inside its middleware — each layer does its "before" work on the way in and its "after" work on the way out, and a guard can bail out before the handler is ever reached.

GuardAllowsUsed on
require_session Any valid session, including one mid-forced-change /change-password
require_active Only a session with must_change == false / and /chat

The middlewares also demonstrate two useful patterns:

  • Auth is centralized. Handlers never parse cookies themselves; they simply declare they need auth.
  • Claims travel in request extensions. After verification, the claims are stored via req.extensions_mut().insert(claims) so a handler can receive them with the Extension<Claims> extractor — see change_password using claims.sub to find the right user.

Code: require_active (auth.rs:476), require_session (auth.rs:512), Extension<Claims> in change_password (auth.rs:600).

What a handler looks like

A handler is the async fn a route calls to produce the response. It takes zero or more extractors (typed inputs pulled out of the request) and returns any type implementing IntoResponse. The HTTP method and path are bound to a handler at registration, so a handler itself never names its route.

// anatomy: extractors in, IntoResponse out
async fn login(
    State(auth): State<Arc<AuthState>>,   // extractor: shared state
    Form(form): Form<LoginForm>,          // extractor: parsed POST body
) -> Response {                            // IntoResponse (redirect + cookie)
    // ...business logic...
}

// registration wires method + path to the handler
Router::new()
    .route("/health", get(health))
    .route("/login", get(login_page).post(login))
    .route("/chat", post(chat))

Because the inputs and output are just Rust types, handlers range from trivial to rich — the method/path wiring stays fixed while the signature does the work:

GET /index (main.rs:99)—Html

Handlers vs middleware, in one line each. A handler computes the response for one route; middleware wraps that computation and decides whether it runs at all. Note change_password: it never reads the cookie itself — the guard runs first, and the handler just declares Extension<Claims> to receive what the middleware verified.

9. Seeding & forced password change

So the app is usable before anyone has an account, it seeds configured emails on first run with a random temporary password printed once to the log. Every seeded account is flagged must_change_password = true.

That flag is the reason require_active exists: even with a valid session, a freshly seeded user can reach only /change-password until they set their own password. On a successful change the server:

  1. re-checks the current password (so a borrowed session cannot silently reset it),
  2. validates the new one (length, confirmation match),
  3. stores a fresh password_hash and clears must_change_password,
  4. re-issues the session cookie with must_change = false.

Code: ensure_seeded (auth.rs:377), login destination logic (auth.rs:585), change_password (auth.rs:598).

Why "change on first login"? A password sent through a log or chat is a shared secret with a short, known lifetime. Forcing a personal password the moment the user is in limits how long that temporary secret is useful.

10. The user store

Accounts live in one JSON document, UserStore { users: Vec<User> }, loaded and saved as a whole. The Storage enum hides where that document lives behind one interface, so the auth logic above does not care:

VariantBacked byUsed when
Storage::FileA local file (USERS_FILE)Development
Storage::GcsA Google Cloud Storage object (USERS_BUCKET)Cloud Run, where the filesystem is ephemeral

This is the repository / abstraction idea: swap the backing store without touching authentication. The GCS variant even fetches its own short-lived OAuth token from the instance metadata server, caching it until near expiry.

Code: Storage (auth.rs:140), load (auth.rs:169), save (auth.rs:188), save_if_absent (auth.rs:200), Gcs::token (auth.rs:242).

Concurrency caveat. The whole document is read-modify-written, so simultaneous writers can lose updates. save_if_absent mitigates the first-write race (via try_exists locally, ifGenerationMatch=0 on GCS) but ordinary concurrent edits are still last-write-wins.

11. Security properties & trade-offs

PropertyHow it is achievedResidual risk
Passwords not recoverable argon2id + per-user salt Weak user passwords still guessable offline if the store leaks
Token cannot be forged or altered HS256 signature with a private secret; algorithm pinned Secret leak = full compromise
Token cannot be stolen via XSS HttpOnly cookie XSS can still act as the user (send requests)
Token not sniffed Secure (over HTTPS) Must be enabled in production
CSRF mitigated SameSite=Lax Lax still allows top-level GET navigations
Stolen token eventually useless exp claim + SESSION_TTL_SECS Valid until expiry — no per-request revocation
The JWT trade-off. Because the server keeps no session table, it cannot "log out" a token that has already been issued — logout only deletes the browser's copy. To truly revoke (e.g. on password change) you need extra server-side state such as a denylist or a token version. Also note that this app's JWT still validates after a password change until it expires; the must_change flag gates routes, but old tokens are not invalidated.

Timing

Login compares the password after looking up the user; a missing user returns early. In principle the tiny timing difference can reveal whether an email exists (user enumeration). argon2's cost dominates the comparison here, which blurs the signal, but a fully hardened login would do a dummy hash even for unknown users.

12. Glossary

Authentication vs authorization
Proving who you are vs. deciding what you may do.
Hash
A one-way fingerprint of data. Cannot be reversed; used to store passwords without keeping them.
Salt
Random per-password data mixed in before hashing so identical passwords hash differently.
argon2id
A modern, memory-hard password-hashing algorithm; the current recommended default.
PHC string
The self-describing $argon2id$... text that bundles algorithm, cost, salt, and hash.
Session
The state (here, a signed token) that lets later requests be recognized without re-entering the password.
JWT
JSON Web Token: a signed, base64url, three-part token carrying claims.
Claim
A name/value assertion inside a JWT payload, e.g. sub, exp, must_change.
HMAC / HS256
A keyed hash used to sign a JWT with one shared secret (symmetric).
Cookie
A server-set value the browser replays automatically; the transport for the session token.
HttpOnly / Secure / SameSite
Cookie flags that block script access, require HTTPS, and limit cross-site sending respectively.
Middleware
Code wrapping a handler that can inspect, reject, or forward the request.
CSRF
Cross-Site Request Forgery: another site making the browser silently send an authenticated request.
XSS
Cross-Site Scripting: injected script running in your origin; HttpOnly limits its access to the token.
TTL
Time-to-live; here how long a session token stays valid.
